# ADR-001: Compiled Hymn Data Strategy

## Status

Accepted (implemented)

## Context

The app serves 640 hymns from the Harpa Cristã. Reading and parsing a JSON file with 640 complex objects at every startup would result in unacceptable loading time, violating the "Excelência na Experiência Principal" pillar.

Two alternatives were considered: (a) ship JSON and parse at runtime, (b) compile hymns as Kotlin code.

## Decision

Compile all 640 hymns as a single Kotlin object (`HymnDataSource.kt`, 545KB, 7420 lines) generated by a separate code generator module (`:generator`). The data is directly compiled into the APK and available in memory from process start.

## Simplest Viable Architecture

A JSON file read via `context.assets.open()` with Gson/Kotlinx Serialization parsing on a background thread.

## Alternatives Considered

### JSON + runtime parsing

Fit: standard approach. Benefits: easy to update, no code generation step. Costs: I/O + parsing at every cold start (~200-400ms for 640 hymns).

### Room/SQLite database

Fit: scalable for large datasets. Benefits: queryable, pagination. Costs: heavyweight for a static dataset, requires migrations.

## Consequences

### Positive

- Instant hymn access (zero I/O, no parsing)
- Search is CPU-only, no disk latency
- No database dependency for static data
- Predictable memory layout

### Negative

- Large source file (7420 lines) — awkward to hand-edit
- Adding/modifying hymns requires re-generation + rebuild
- Generator module must be maintained separately

### Operational

- Hymn updates require a full app release
- No over-the-air hymn data updates possible

### Testing

- Hymn data is always available in tests without mocking

## Future Evolution Triggers

- Hymn count exceeds 2000
- Need for OTA updates without app release
- Need for user-contributed hymn content
- Multi-language hymn support

## Risks

- HymnDataSource.kt is too large for IDE performance on low-end machines
- Generator module is undocumented (no visible generator source in repo)
